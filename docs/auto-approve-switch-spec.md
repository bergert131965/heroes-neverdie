# 自动同意开关 — 逻辑规格（待确认，未实现）

> 本文只定义「开关怎么工作」，不新增设计。探针已确认本地客户端插件可挂载（见 `auto-approve-evaluation.md` §零），
> 因此插件形态按已实测通过的骨架来定。

---

## 一、插件在桌面端内的落位

插件**整体属于桌面端自有**，不修改任何官方包，不进 `@deepseek-ai/*`，与 `desktop-runtime.js` 同级：

```
heroes-neverdie/
├── profile/
│   ├── cordis.patch.yml            ← 加一行 insert 挂载本插件（唯一改动的既有文件）
│   └── plugins/
│       └── auto-approve/           ← 新增：宿主半侧（Node）
│           ├── package.json        ← dsh.client 声明（platform=web, exports["./client"]）
│           ├── index.js            ← 宿主半侧：提供设置命名空间 + 空闲状态服务
│           └── client.js           ← 浏览器半侧：设置开关 UI + 倒计时 + 自动应答
```

实测约束（必须遵守，来自探针）：
1. 宿主半侧与浏览器半侧**必须两个文件**；
2. `cordis.patch.yml` 的行**必须指向 `index.js`**，不能指向目录；
3. `package.json` 必须有 `dsh.client.platform = "web"` 与 `exports["./client"]`。

## 二、开关在「设置」里的位置与外观

放在 **设置 → 权限** 分区（与既有的「选择新会话的默认权限模式」同一区），因为它属于权限语义，不埋进通用设置：

```
权限
  选择新会话的默认权限模式     [工作区内修改 ▾]

  审批空闲自动同意                [ ○──]   ← 新增一行（默认关闭）
  5 秒内无操作时自动同意待审批请求。
  仅在窗口未聚焦或键盘鼠标连续空闲时生效。
```

- 交互元件：开关（toggle），不是下拉。
- 文案：中英双语，走既有 locale 机制。
- 首次开启：弹一次风险确认（复用「完全权限」那档的确认弹窗模式，`dsh-client-ui-permission-presets/lib/client.js:32-40`）。
- 关闭时该行不产生任何副作用。

## 三、开关的逻辑（逐条）

### 3.1 状态

| 项 | 定义 |
|---|---|
| 存储 | 新设置命名空间（例 `auto-approve`），落在 `~/.dsh/settings.yaml`，与 CLI/网页版共享 |
| 默认值 | `false`（关闭） |
| 作用域 | 全局（跨会话）；不改写会话的持久权限策略 |
| 重启保持 | 是（走既有 settings 服务，非内存态） |

### 3.2 生效条件（**四条全满足**才自动同意）

1. 开关为开；
2. 该会话处于 `ask` 策略下（`never` 策略根本不会走到渲染端，开关对其天然无效）；
3. 存在一个待审批请求（面板已弹出）；
4. **空闲判定成立**：窗口未聚焦，**或**键盘/鼠标连续无输入已达到阈值。

任一条不满足 → 与现状完全一致，必须人工点击。

### 3.3 倒计时行为（待你确认，见 §四）

- 触发后从 5 秒开始倒数；
- 期间任何用户动作（点击、按键、鼠标移动、窗口重新聚焦）→ **立即取消倒计时**，回到普通人工确认；
- 倒计时结束时 → 自动提交 `allowed-once`（即面板上「允许一次」那一次点击）；
- 每次请求只结算一次，自动提交后若用户再点，必须被吞掉而不报错（官方 `PendingApproval.finish()` 二次结算会抛 `already settled`，`dsh-client-ui-approval/lib/client.js:203-205`）。

### 3.4 明确不做的事

- **不**自动点击「拒绝」；
- **不**自动确认「启用完全权限」这类风险弹窗；
- **不**改写会话持久策略、**不**影响 `never`；
- **不**在没有待审批请求时做任何事。

### 3.5 安全护栏（与开关同时上线）

| 护栏 | 默认 |
|---|---|
| 首次开启风险确认弹窗 | 强制 |
| 仅对 `allowed-once` 生效 | 强制 |
| 每会话自动同意次数上限 | 建议 10 次，超限回退人工 |
| 删除/写入类工具的豁免白名单 | 建议第一阶段硬编码 |
| 触发后留可见记录（会话内提示） | 建议 |

## 四、最终确定的三个决策（2026-09-16 用户确认）

| 决策 | 选定 | 含义 |
|---|---|---|
| 倒计时起点 | **A** | 仅当窗口未聚焦，或弹窗出现时窗口已聚焦且键鼠已连续静止 ≥ 10 秒，才开始 5 秒倒数 |
| 空闲阈值 N | **10 秒** | 窗口失焦时 N = 0（立即开始倒数）；窗口聚焦时为 10 秒 |
| 面板倒计时显示 | **静默倒数** | 第一阶段不改变官方面板外观，不显示「5 秒后自动允许」 |

### 由此确定的完整判定链

```
待审批请求出现
  ├─ 开关关闭？                         → 人工确认（现状）
  ├─ 会话策略 = never？                 → 不会走到这里，天然无效
  ├─ 窗口未聚焦？                       → 立即开始 5 秒倒数
  ├─ 窗口聚焦 且 键鼠静止 ≥ 10 秒？      → 开始 5 秒倒数
  └─ 其它（窗口聚焦且有近期输入）        → 人工确认（现状）

倒数中：
  ├─ 任何点击 / 按键 / 鼠标移动 / 窗口重新聚焦 → 取消倒数，退回人工确认
  └─ 满 5 秒                                 → 自动提交 allowed-once（仅一次）
```

### 由此产生的两条实现要求

1. **宿主半侧需要暴露窗口聚焦态**：倒计时判定依赖「窗口是否聚焦」。候选实现是从 `desktopShell` 透出 `browserWindow.isFocused()`，并经既有 IPC 载体读给渲染端；主进程侧只加读取口，不改桥的结构。
2. **渲染端需要输入空闲计时**：监听 `pointerdown` / `pointermove` / `keydown` / `focus` / `blur` / `visibilitychange`，维护「最近一次输入时间戳」。这一段可以放在插件自己的浏览器半侧，不必改 `desktop-runtime.js` 的传输前置脚本。

### 静默倒数的可观测性补偿

面板不显示倒计时，因此"用户如何知道刚才那一步是机器替他点的"必须另行给出：按 §3.5 的护栏，自动同意命中时在会话内留一条可见记录（第一阶段用会话内提示即可）。

## 五、确认后的落地顺序

1. 设置命名空间 + 开关行（可见、可持久化）—— 先给你看效果；
2. 空闲检测（宿主半侧窗口聚焦态 + 渲染端输入计时）；
3. 倒计时与自动应答（含防重、上限、可见记录）；
4. 风险确认弹窗与工具豁免；
5. 按评估文档 §七 的 V1–V4 验收。
